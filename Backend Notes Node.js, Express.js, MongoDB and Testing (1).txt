How to use these notes
By the end of these notes you will have built the backend for StudentDesk, a React app
that lists, adds and deletes students. Your friend's React app (the frontend) is already
built. You will build the part behind it: a Node.js and Express.js API that saves students in

backend.

understand the example, the task is the same pattern applied to the real project.

Setup 1: Install Node.js, VS Code and Git
Explanation
Why: JavaScript normally runs only inside a browser. Node.js lets it run on your computer,
which is what a backend needs. Installing Node.js also installs npm (Node Package
Manager), which downloads libraries such as Express for you. VS Code is where you write
the code, Thunder Client lets you send test requests to your API, and Git saves versions
of your project and uploads it to GitHub.
What you get: the commands node , npm and git work in your terminal.
Why LTS: LTS means Long Term Support. It is the stable version that companies use, so
choose LTS rather than "Current".

Setup 2: MongoDB Atlas (cloud.mongodb.com)
Explanation
Why: a backend needs somewhere to keep data permanently. If you store students in a
JavaScript array, they disappear every time the server restarts. MongoDB is a database
that stores data as JSON-like documents, so it feels natural in JavaScript. MongoDB Atlas
is MongoDB running in the cloud, so you don't install a database on your laptop.
What you get: a free database in the cloud, a username and password to log into it, and a
connection string: the address your Node.js code uses to reach it.

Setup 4: .env, .gitignore and a Git repository
Explanation
Why .env : your connection string contains your database password. If you type it
directly in your code and push the code to GitHub, anyone can read it and use your
database. A .env file keeps secrets outside your code. Your code reads them with
process.env.MONGO_URI .

Why .gitignore : it lists files that Git must never save or upload. We ignore:
.env , because it holds the password.
node_modules , because it is huge (thousands of files) and anyone can recreate it with
npm install .

Why Git and GitHub: Git saves snapshots ("commits") of your project, so you can see
what changed and go back if something breaks. GitHub stores those snapshots online, so
you can share the project and submit assignments.
What you get: a project on GitHub with all your code, but without your password and
without node_modules .

Node 2: Sync vs async (non-blocking)
Explanation
Why we do this: some jobs are slow: reading a file, or asking MongoDB for students. If the
server waited for each slow job before doing anything else, 50 users would be served one
by one. Node is non-blocking: it starts the slow job, carries on with other work, and comes
back when the result is ready. Every database call in your backend works this way, so you
need to understand it before writing await Student.find() .
An everyday picture: making Maggi. Sync = you stand at the stove staring for 2 minutes.
Async = you set the table while the noodles cook, and serve them when the timer rings.
What we get as a result: the output does not appear in the order the code is written. The
async result arrives later.

Node 3: A server with the http module
Explanation
Why we do this: a backend is a server: a program that keeps running and waits for
requests, then sends back responses. Before using Express, we build one with only Node,
so you can see what a server really does and why Express is useful.
The key ideas:
Client: whoever sends a request: the browser, Thunder Client, or the React app.
Server: the program that answers. createServer makes a server program, which runs
inside Node on your laptop.
Port: a door number on your computer. Only one program can use a port at a time. Our
API will use 5000; React uses 5173.
localhost : "this same computer".

What we get as a result: the terminal shows Server running... and does not return to
the prompt, because the server stays on, waiting. Visiting URLs in the browser shows
different answers.
The flow of one visit: you open localhost:3000/students → the browser sends a
request → Node runs your function with req and res → your code checks req.url →
res.end(...) sends the answer → the browser shows it. This repeats for every visit.

Why this syntax:
Code

Node's built-in module for servers

Makes a server. Node calls your function

The path asked for, like "/students"

req.method

The type of request: "GET" , "POST" ...

res (response)

How you answer. You write into it

The status code: 200 OK, 404 Not found...

const http = require("http");
const students = [
{ name: "Asha", department: "CSE" },
{ name: "Rahul", department: "ECE" },
];
const server = http.createServer((req, res) => {
console.log(req.method, req.url);
if (req.url === "/") {
res.end("Welcome to StudentDesk");
} else if (req.url === "/students") {
res.setHeader("Content-Type", "application/json");
res.end(JSON.stringify(students));
} else {
res.statusCode = 404;
res.end("Not found");
}
});
server.listen(3000, () => {
console.log("Server running on port 3000");
});

Express 3: Middleware and CORS
Explanation
Why we do this: some jobs must happen for many requests, not just one route: printing a
log line, checking who is allowed in, reading JSON, giving the React app permission.
Instead of repeating that code in every route, we write it once as middleware: a function
that runs between the request arriving and the route handler.
An everyday picture: middleware is the security guard at the gate. Every visitor passes
the guard. The guard can write down their name (logger), check their ID card ( checkKey ),
or turn them away, before they reach the room (the route).
The flow:
Request → logger (everyone) → checkKey (only /secret) → route handler →
Response

The one rule: every middleware must either call next() (let the request continue) or
send a response (stop it here). If it does neither, the request is stuck and the browser
loads forever.
What CORS is: the React app runs on localhost:5173 and the API on localhost:5000 .
A different port is a different origin. For safety, browsers block a page from reading
another origin's data, unless that server says it's allowed. app.use(cors()) is middleware
that adds the permission header Access-Control-Allow-Origin: * to every response.
Thunder Client is not a browser, so it never shows CORS errors. That is why an API can
work in Thunder Client and still fail in React.
What we get as a result: a log line in the terminal for every request, a protected route, and
a React app that is allowed to call our API.

2. Send a request with Supertest.
